# SNHPC Game Bringer & Game Rotation technical assessment

**Recommendation:** Build **Bring a Game** around private offers and a separately reviewed member-facing listing. Build **Game Rotation** around existing catalog, lender, and location records, with private coordination data alongside them. Keep offers and plans out of the live lineup until a move actually happens.

The staging catalog can store two rows with the same title under different slugs, but its lineup and Pinball Map integration cannot reliably track those rows as two separate cabinets. The first release can accept two separate offers for the same title. If coordinators also need to track both physical copies independently from day one, establish cabinet identity before shipping rotation confirmation.

This assessment reviews staging at commit `707bec5faeff7d60a4e553b636fc42b71cddd46a` through GitHub, including schema migrations, application code, and repository documentation. The verified findings describe that commit. Hosted schema parity, live data, and runtime configuration remain unverified. [Reviewed staging commit](https://github.com/joshmaz/pinball-club-website/commit/707bec5faeff7d60a4e553b636fc42b71cddd46a)

## Proposed data model and workflow

The names and boundaries below are proposals. The three records that matter operationally are the **catalog title or edition**, the **specific cabinet being offered or moved**, and the **cabinet’s placement at the club**.

| Proposed record | Minimum contents and behavior |
|---|---|
| **Game offer** | One submission for one cabinet. Record the submitting member, optional catalog game, exact OPDB ID where known, fallback title, condition, approximate availability, open-ended or approximate loan terms, and transport considerations. Keep submitter, lender, condition details, and logistics private. Track review and withdrawal separately from publication and from any rotation plan. Reuse an existing lender party when confirmed. The submitter and lender may be different people. |
| **Published candidate** | Store a small, reviewed projection on the offer initially, with publication metadata and an explicit member-facing description. The browse endpoint returns only allowlisted fields such as title, edition, approved summary, and interest state. Keep stable private identifiers, lender affiliation, and raw free text out of the response. Member edits should require re-review before edited content appears. Withdrawal should remove the candidate from browse immediately. |
| **Offer interest** | One row per offer and member, enforced by a unique pair. Make “I’d play this!” reversible and safe to retry. Require a currently published candidate for new interest. Display counts if approved, with individual voter identities private by default. |
| **Placement details** | Add a private companion keyed to the existing stint for the first release, provided one stint is sufficient for the agreed placement scope. Store the lender party at placement time, club-owned or loan classification, optional terms, rotation or return-request state, and a private coordination note. Leave legacy stints unclassified until someone verifies them. If one loan needs durable continuity across venue moves, use one private loan record linked to multiple stints instead of copying terms to every stint. |
| **Rotation plan** | Allow an incoming offer, an outgoing placement, or both. Track tentative timing, a private coordination note, and independent confirmation for each side. Link a confirmed arrival to the actual stint. Confirming a departure records the actual departure against its placement. Canceling a plan leaves location history intact. Use transactional confirmation with retry protection and checks for competing active plans for the same placement or offer. |

Use one editable private note per relevant record initially. Add a note history only if coordinators need multiple authored entries. Derive **Needs Attention** from new offers, requested returns, incomplete moves, and an optional manual follow-up flag or date. A follow-up date is a prompt to check in. Planned and approximate dates never close stints or trigger departures automatically.

**Cabinet identity decision.** For a first release with one independently tracked cabinet per catalog title or edition at a time, an offer can identify the proposed cabinet and a confirmed stint can identify its placement. Flag ambiguous matches and require coordinator reconciliation. If overlapping copies, recurring cabinet identity, cabinet-specific maintenance, or same-title swaps require independent tracking, introduce one canonical cabinet entity linked to the catalog game and use it on offers and stints. Move cabinet-level ownership to the canonical cabinet relationship as part of that work. Preserve existing title pages and explicitly reconcile Pinball Map observations at title level when they provide insufficient evidence to identify a cabinet.

**Lineup changes.** Start with a handoff to the existing Games Editor for catalog creation and changes to shared lineup or stint records. Game Rotation can link and reconcile the records once verified. If coordinators should execute arrivals and departures directly, give them a narrow, audited confirmation operation after proving how it interacts with Pinball Map, manual overrides, and simultaneous or same-title moves. A plan becoming due has no effect on the lineup.

## Proposed permissions

Permissions are additive when someone holds multiple responsibilities. “Member” means an eligible portal account, with the eligibility rule still to be confirmed.

| Capability | Member | Games Editor only | Game Coordinator | Board designation only | Website Administrator |
|---|---|---|---|---|---|
| Submit, see, edit, or withdraw own offers | Own | Own | Own | Own | Own |
| Browse published candidates and toggle own interest | Yes | Yes | Yes | Yes | Yes |
| Read all offers, private coordination notes, and needed placement/lender data | — | — | Yes | Read-only oversight, proposed | Yes |
| Review, publish, unpublish, and manage rotation plans | — | — | Yes | — | Yes |
| Edit catalog metadata and existing Games-domain records | — | Existing access | Via separate Games role | Via separate Games role | Existing access |
| Grant or revoke Game Coordinator | — | — | — | — | Yes, plus Membership Admin if approved |
| Read full Operations messaging and administrative audit history | — | — | — | — | Existing access |

Anonymous users have no access to offer, interest, or rotation data. Enforce this at the database and API boundary. Use private base data and purpose-specific authenticated reads and writes for **My offers**, **Published candidates**, and **Game Rotation**. Derive the caller from the authenticated session. Check ownership, capability, allowed fields, and valid transitions on every write. Test direct reads and RPC calls, including catalog attribution, public snapshots, and notification previews. Existing Games Editor access to the owner directory remains a separate capability.

Add the coordinator assignment to the SQL allowlist, effective capability checks, Member Tools presentation, and delegation rules together. The canonical policy also derives `website_volunteer` from recognized assignments, so a coordinator assignment may grant existing shared Club Issues privileges. Confirm that inheritance before implementation. Board oversight can be read-only without exposing Operations or giving staff the same rotation access by default. [Role policy](https://github.com/joshmaz/pinball-club-website/blob/707bec5faeff7d60a4e553b636fc42b71cddd46a/docs/website-roles-and-authorization-policy.md), [Existing role-domain migration pattern](https://github.com/joshmaz/pinball-club-website/blob/707bec5faeff7d60a4e553b636fc42b71cddd46a/supabase/migrations/20261017180000_publishing_role_domain.sql)

## Proposed UI

- **Bring a Game** is a standalone authenticated page linked from the member dashboard. It has **Offer a game**, **My offers**, and **Published candidates** sections. The form searches the catalog first, then OPDB, with manual entry available. My offers shows whether an offer is under review, published for feedback, being coordinated, or closed. Candidate cards carry the approved summary and “I’d play this!” control. Use “Published for member feedback” to distinguish that state from a planned arrival.
- **Game Rotation** is a separate role-gated Member Tools entry. Lead with **Needs Attention**, then **Offers**, **Current lineup**, and **Planned moves**. Offer detail shows a preview of what members will see alongside the private review fields. Current lineup links to existing game records and displays lender, rotation openness, and return requests as permitted. Planned moves accepts an arrival, a departure, or a pairing, with separate actual confirmation for each move.
- Reuse shared session handling, styles, form/status patterns, and validated portal deep links. Keep rotation UI in a dedicated module. The existing Games panel remains the entry point for catalog edits during the initial handoff workflow. ## Implementation phases and acceptance criteria

| Phase | Acceptance criteria |
|---|---|
| **0. Confirm scope and inventory assumptions** | Agree on cabinet identity, Board oversight, role delegation, membership eligibility, and the move-confirmation owner. Before implementation, reconcile the migration ledger in each environment and inspect representative duplicate-title, unknown-lender, current-lineup, and multi-venue cases using authorized read-only access. Document how ambiguous catalog and stint matches will be handled. |
| **1. Offers, review, and member interest** | A member can submit a catalog match, exact OPDB edition, or manual title and track or withdraw it. A coordinator can review and explicitly publish an approved summary. Two offers for the same title remain distinct. A second member can see only the published fields and toggle interest once. An ordinary member and a Games Editor acting without the coordinator role cannot access another member’s draft or internal notes. |
| **2. Lineup, placements, and rotation** | Coordinators can work from the existing lineup, link a verified lender, record open-ended or approximate terms and return requests, and create arrival-only, departure-only, or paired plans. Each confirmed move links to the actual lineup history. A retried confirmation has one effect. Canceling or rescheduling a plan leaves actual history intact. Legacy records with unresolved cabinet or lender identity are visible for reconciliation. |
| **3. Notifications and staging pilot** | Reuse the existing dispatcher for a small initial event set, such as new offers to coordinators and selected status changes to submitters. Each event/recipient pair queues once. Staging previews render to the configured test address, and coordinator alerts stay within the shared delivery budget. During the pilot, verify the complete member-to-coordinator flow and the Games Editor handoff before enabling production access. |

### Testing, migration, and deployment

- **Authorization and privacy.** Use the existing SQL test patterns to exercise anonymous, member A, member B, Games Editor, coordinator, Board, staff, and administrator identities. Include escalation through direct API calls, stale forms after role revocation, a member attempting to edit publication fields, withdrawn candidate links, owner inference through shared game links, and account deletion or lender reassignment. Decide offer retention and whether historical submitter references should be cleared or preserved under the existing account-deletion rules.
- **Data integrity and compatibility.** Test open-ended and approximate terms, club-owned machines, unknown legacy dates, a lender change, a venue move during a loan, same-title substitutions, double confirmation, and Pinball Map ingest before and after a confirmed move. Preserve game IDs, slugs, public snapshots, image associations, scores, Pingolf, issues, and existing public history behavior. Use additive migrations and leave ambiguous legacy relationships for manual reconciliation. [Public snapshot contract](https://github.com/joshmaz/pinball-club-website/blob/707bec5faeff7d60a4e553b636fc42b71cddd46a/docs/public-snapshots.md)
- **Email and audit.** Enqueue from the authorized transaction with a stable event key. Keep private notes and logistics out of email and audit payloads. Existing signup notices authorize recipients at enqueue time, so decide whether queued coordinator notices should be rechecked on dispatch after a role revocation. Test queue deduplication, retry behavior, and staging test delivery. Audit role changes, publication, return requests, plan changes, and move confirmation using actors, record IDs, and state transitions. The documented live limit is shared across notification types and currently capped at ten messages per rolling 24 hours. Avoid a notification per interest click. [Email safeguards](https://github.com/joshmaz/pinball-club-website/blob/707bec5faeff7d60a4e553b636fc42b71cddd46a/docs/email.md), [Audit design](https://github.com/joshmaz/pinball-club-website/blob/707bec5faeff7d60a4e553b636fc42b71cddd46a/docs/audit-logging-design.md)
- **Release sequencing.** The repository workflow deploys site changes from `staging` and `main`. After approval, coordinate backward-compatible database changes with front-end deployment. Validate against a disposable database first, then pilot on staging with separate member, coordinator, and oversight accounts. Verify environment-specific mail settings before enabling notifications. Keep a way to disable feature entry points and notification enqueueing while preserving submitted offers and placement history. ## Outstanding product decisions

1. **Physical cabinets.** Must the first release track two copies of the same title or edition simultaneously, recognize a returning cabinet, or record a same-title swap while the title stays on the floor?
2. **Authority.** Is the existing Board designation sufficient for oversight? Should Board see lender contact details and all private notes? May Membership Admin appoint coordinators, and may coordinators confirm actual lineup changes themselves?
3. **Who can offer.** Does eligibility include all signed-in portal members, verified accounts, or active paid members? Should coordinators be able to enter offers on behalf of outside lenders?
4. **Publication and attribution.** Which fields may appear on candidate cards? Can a lender opt into attribution, and does that permission carry forward to the public Games page after arrival? Should interest counts be visible to members, coordinators, or both?
5. **Lending history and follow-up.** Does one loan need to stay identifiable across venue changes? Who may request a return in the portal, and which events merit email versus a Needs Attention item?
6. **Edits and retention.** What should happen to an already published candidate after a material member edit? How long should withdrawn offers, interest, and private notes be retained after closure or account deletion?

The cabinet decision determines whether rotation can start with a private extension to existing stints or needs a canonical cabinet record first. The member offer and publication workflow can proceed under either approved model.
